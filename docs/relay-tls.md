# Relay TLS in the desktop app

How the relay that the desktop app hosts does TLS, and what is and is not
pinned.

This used to be a runbook for a deployment model that no longer exists. There is
no relay to deploy, no container, no compose file and no `RELAY_CERT_DIR`. The
relay is a background task inside the desktop app
(`apps/desktop/src-tauri/src/relay.rs`), and everything below follows from that.

## 1. How the certificate is decided

There are two independent pieces of configuration, and both now come from the
desktop's Settings:

| Concern | Setting | Client setting |
|---|---|---|
| Name in the certificate | `relay_hostname` | the hostname in the relay URL |
| Certificate trust | the key pair under the cert directory | the pin from `GET /pin` |

If the first pair disagrees, the client fails **hostname verification**. If the
second pair disagrees, the client fails **pin verification**. The two failures
look identical from the client ("certificate error"), so check both.

The details that used to be operator instructions:

| Concern | Where it comes from now |
|---|---|
| Name in the generated certificate | the **`relay_hostname` setting**, passed to the relay as `Overrides::tls_hostname` (`relay.rs:474`). There is no `RELAY_TLS_HOSTNAME`. |
| Extra SANs | `Overrides::tls_extra_sans`. The desktop does not set any; the library default of `localhost`, `127.0.0.1` and `::1` applies. |
| Where the certificate and key live | `app_data_dir()/relay-certs` (`relay.rs:473`), so `cert.pem` and `key.pem` sit with the rest of the app's state. There is no `RELAY_CERT_DIR`. |
| The relay's TLS port | the `relay_port` setting, **9529**. Not 9528. |
| Its health / metrics / pin port | the `relay_health_port` setting, **9530**, and it is **loopback-only by construction** — see §3. |

Leaving `relay_hostname` empty means "localhost", which is correct while you are
testing and wrong the moment a phone on another network dials a real name. It is
the single most common cause of a relay that works locally and fails everywhere
else, and it is the one field worth setting before you expose the port.

Self-signed is the only option: the certificate is generated by the relay itself
from the names above. If you want a real certificate, see §4.

## 2. Pin algorithm

**`sha256/` + base64( SHA-256( DER SubjectPublicKeyInfo ) )**

The pin covers the certificate's **public key only**, not the whole
certificate. That is deliberate:

- The pin survives certificate renewal as long as the key pair is reused. A
  whole-certificate pin must be redistributed at every renewal, which is how
  teams end up disabling pinning.
- `sha256(SPKI-DER) != sha256(cert-DER)`. These are **different values**. An
  earlier version of this repo documented an SPKI pin while the only client
  that implemented pinning hashed `cert.der` — the documented pin could never
  match, and every connection was rejected.

The pin is computed from the certificate the relay actually loaded, at startup,
from the parsed certificate rather than from the PEM text, so it cannot be
computed over the wrong file. `scripts/generate-cert-pin.sh` prefers the served
endpoint and falls back to `openssl` only if the endpoint is unreachable.

> **Still true, and now live rather than hypothetical: the mobile client**
> (`apps/mobile/lib/services/websocket_service.dart`)
> **still hashes the whole DER certificate.** It must be changed to hash the
> SPKI before mobile pinning works. The desktop app has no pin configuration
> target at all — `VITE_RELAY_CERT_SHA256` was deliberately removed from the
> project.
>
> This used to be a latent defect behind a relay nobody ran by default. The
> relay is **on by default** now, so the gap is reachable on a normal install:
> any phone that pins will fail, and the desktop will not warn about it.

## 3. Reading the pin

The relay serves the pin from the certificate it actually loaded:

```bash
curl -s http://127.0.0.1:9530/pin
# {"sha256":"sha256/0Q2m…","algorithm":"spki-sha256"}
```

`/pin` is unauthenticated, like `/healthz`, and that is acceptable **because of
where it is published**: the health surface is pinned to loopback in the
desktop's `build_config` (`relay.rs:466`) and is deliberately *not*
environment-overridable — there is a test that sets `RELAY_HEALTH_BIND=0.0.0.0`
and asserts the effective bind is still `127.0.0.1`
(`the_health_surface_is_always_loopback`, `relay.rs:512-523`). The same port is
also where the peer count and the metrics live. There is no published version of
this endpoint on any routable address.

Or use the helper, which prefers `/pin` and falls back to openssl (and refuses
to print a pin when `openssl x509 -checkhost` says the certificate is not valid
for the requested name):

```bash
scripts/generate-cert-pin.sh relay.example.com 9529
scripts/generate-cert-pin.sh relay.example.com 9529 --health-port 9530
```

Then:

- **mobile** — Settings → pinned certificate, or
  `websocketService.setPinnedCertificate('sha256/…')`.
  **The client code must hash the SPKI, not `cert.der`** (§2).
- **desktop** — no configuration target exists today; the project removed
  `VITE_RELAY_CERT_SHA256`. Until one is added, re-check `/pin` after every
  renewal.

## 4. Bringing your own certificate

Put `cert.pem` (full chain, leaf first) and `key.pem` in
`app_data_dir()/relay-certs` before the relay starts. The relay loads them if they
are there and generates a self-signed pair if they are not, so this is a matter
of writing the two files into that directory — there is no path to configure and
no volume to mount.

Accepted private-key formats — **all three are auto-detected**:

| Format | PEM header | Typical producer |
|---|---|---|
| PKCS#8 | `-----BEGIN PRIVATE KEY-----` | `openssl genpkey`, certbot (modern) |
| PKCS#1 | `-----BEGIN RSA PRIVATE KEY-----` | `openssl rsa -traditional`, older certbot, Windows exports |
| SEC1 | `-----BEGIN EC PRIVATE KEY-----` | `openssl ecparam`, older tooling |

> The relay previously used `rustls_pemfile::pkcs8_private_keys`, which silently
> yielded **zero** keys for PKCS#1 and SEC1 files and then reported the
> misleading *"No private keys found in key file"* — text that `openssl
> rsa -traditional`, older certbot and Windows exports all produce by default.
> The current message names the three accepted armours and counts what it found,
> so a genuinely keyless file is now distinguishable from an unsupported one.

The relay tightens `key.pem` to `0600` on startup (unix only) and **fails
closed** if the key and certificate do not belong together.

**ACME/Let's Encrypt integration is deliberately not built in**, and it is more
obviously correct now that the relay is in-process: an HTTP-01 challenge needs
port 80 and a publicly reachable address; an `rustls-acme`-style in-process
client has to renew in the background and hot-swap a certificate, and the relay
deliberately loads its certificate once at startup (§5). Running certbot (or any
external ACME client) against the same directory is simpler and fails loudly in
a place you can see — write `fullchain.pem` and `privkey.pem` into the cert
directory before launching the desktop app.

If a TLS-terminating proxy sits in front of the relay, note that the proxy
presents **its own** certificate, so pin the proxy's certificate, not the
relay's. The relay's TLS port is **9529**; the proxy forwards to that, and there
is no separate relay service to name.

## 5. Renewal and restart

The certificate is read **once, at startup**. There is no hot reload.

```powershell
# Restart the desktop app. That is what restarts the relay.
```

The pin is stable across a renewal **as long as the key pair is reused**. If you
issue a new key, the pin changes and every client must be updated — check
`GET /pin` after any renewal.

## 6. Troubleshooting

| Symptom | Cause | Fix |
|---|---|---|
| Client rejects with a hostname/certificate error | `relay_hostname` not set, so the cert is only valid for `localhost` | set `relay_hostname` in Settings, delete the cert directory and restart the app to regenerate |
| Client rejects a pin it should accept | client hashes `cert.der`, pin is over the SPKI | client must hash the SPKI (§2) |
| Pin changed unexpectedly | certificate was reissued with a **new key** | reuse the existing key, or redistribute the pin |
| Phone cannot reach the relay at all | nothing has made port 9529 reachable from the other network | a router port-forward, a VPN or a tunnel. Conduit does not do this for you |
| `curl http://<desktop-ip>:9530/pin` hangs or is refused | correct behaviour: the health surface is loopback-only | use `http://127.0.0.1:9530/pin` on the desktop itself |
| `No private key found in key PEM — expected one of …` | the file contains no recognised `PRIVATE KEY` block | check the file actually contains a key |
| `Failed to parse private key as RSA, ECDSA, or EdDSA` | PEM armour is recognised but the body is not a valid key | re-export with `openssl pkcs8 -topk8 -nocrypt` |
| `TLS config error` at startup | cert and key do not belong together | re-issue both from the same key |
| Relay does not start, and Settings shows why | a config or bind failure is recorded rather than fatal | the message names the port; the desktop carries on LAN-only |
| Pin helper exits 2 | `openssl x509 -checkhost` failed — something other than your relay answered | do **not** pin; fix DNS/hostname first |

Relevant source: `services/relay/src/tls.rs`,
`apps/desktop/src-tauri/src/relay.rs`, `scripts/generate-cert-pin.sh`.
